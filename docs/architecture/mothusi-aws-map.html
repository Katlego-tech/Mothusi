01 · The project

What Mothusi is

Mothusi is a digital colleague for South African teachers that takes over the assessment cycle. The teacher hands it the memo and the class's scripts as they are: photos, scans or PDFs of handwritten work. Mothusi sits the test to check the memo, marks every script against the memo while quoting the evidence for each mark, re-marks a blind sample the way a head of department moderates, and checks every total and weighting in code. It then produces the mark sheet, item analysis, catch-up plan and a note for each learner. Nothing reaches a learner or parent until the teacher approves it.

It is built for the Colleague Zero hackathon (13–14 Nov 2026) for a Grade 10 Mathematics teacher, three classes of 45, a head of department who wants the moderated mark sheet by Friday, and a phone as her main computer. Grade 10 Mathematics comes first, then Accounting as the second curriculum pack on the same code. A voice colleague in the console reports progress, explains a mark, asks the teacher Mothusi's questions and briefs her on the results.

The models run on Mothusi's own GPU in Cape Town (option A). Section 04 keeps all five options that were weighed, from that GPU to Claude on Bedrock. The deciding questions were what leaves South Africa, how well each option marks, and what each costs.

One assessment, start to finish

  1. Intake reads each page, crops off the cover with the name, and swaps names for pseudonyms before any model sees the work.
  2. Setter sits the test against the memo and flags memo errors for the teacher.
  3. Marker marks every script, quoting the answer and the memo line for each mark.
  4. Rules in code check totals, bounds, evidence quotes and weightings, and send failures back.
  5. Moderator re-marks a blind sample without seeing the first marks, on a model from a different family.
  6. Analyst and Support find the misconceptions and plan catch-up in the remaining ATP weeks.
  7. Writer and Reviewer draft each learner's note and reject any that is ungrounded or unkind.
  8. Teacher approves the bundle in the console. This gate cannot be skipped.
  9. Executor writes the mark sheet, the PDF moderation report and the learner notes, then releases them. It calls no model.
02 · The learner side

In the core build, learners never log in and never talk to a model (the stretch learner section in 03 adds a sign-in). After the teacher approves, each learner gets one note, and every part of it is checked in code before the teacher sees it. 03 · Stretch features

The learner section: practice tests and the exhibition hall

Both were recorded as stretch on 8 Nov (the agreed scope and the voice-and-stretch note §2–3 on the unmerged voice branch) (source note not in this repo). Today's changes: the exhibition hall narrows to Mathematics and Accounting, uses 3D models sourced from Sketchfab, and is narrated by ElevenLabs. Learner sign-in

Learners sign in with a code and PIN that the teacher hands out. The account name is the learner's pseudonym code, so Cognito holds no name, email or phone number, and the class list that maps codes to names stays inside Mothusi. A learner account is still a child's personal information, so it needs a parent's consent first (POPIA s35(1)(a)).

Option A · Everything in Cape Town on EC2 G4dn

decided · deployed

Why

  • No learner data leaves South Africa, including what the models read.
  • mothusi_llm's Ollama provider already works, so the G4dn needs no new adapter, and qwen3:14b is already on the laptop.
  • Billed per GPU hour (g4dn.xlarge $0.698/h in Cape Town), and the instance can be stopped between sets.
  • The same models run on the laptop fallback, so the prompts are tuned once.
  • A managed variant exists: SageMaker real-time endpoints on ml.g4dn run in Cape Town too ($0.977/h for xlarge).

Watch

  • Capacity, not quota. The quota was granted 11 Nov. g4dn.xlarge is offered only in af-south-1b and 1c, so the host sits in 1b, and on 12 Nov a start was refused for about 2½ minutes (InsufficientInstanceCapacity). ops.sh now starts the GPU before RDS, so a refusal costs nothing.
  • Speed, measured 12 Nov. The T4 is an older GPU: 16 GB, fp16 only, no FlashAttention-2. qwen3:14b decodes about 17 tokens/s alone and about 25 tokens/s across four requests at once, so the host serves 4 in parallel and the Planner marks in batches of 4. A Marker call still takes 64 s at the median (110 s at p95), over the 30 s target. Thinking is off for every role.
  • Ollama loads one model at a time (a cold load of qwen3:14b took 75 s), so each swap between reader, marker and moderator costs time. A g4dn.12xlarge (four T4s) keeps them all loaded.
  • In the 12 Nov eval every phi4 Moderator call hit the 180 s client timeout. The cause is being investigated.
  • No model card publishes a handwriting score. Open models may mark less accurately than Claude; the rules in code turn bad marks into logged retries, and the eval measures agreement.
  • Gemma 3 and 4 are unstable on a T4 in fp16, so we avoid them.

Option B · Cape Town data, open models on Bedrock in the EU

data crosses

Why

  • Models far larger than a T4 holds, including a vision model (Qwen3-VL-235B) running in-region in Ireland.
  • No GPU for us to run or patch.
  • Billed per token, with nothing running between sets.

Watch

  • Learner-derived data leaves South Africa: s72(1)(a).
  • Still paid per token. Third-party Bedrock models may be billed through AWS Marketplace, which credits usually do not cover (unverified).
  • A new mothusi_llm adapter (Bedrock Converse).

Option C · Everything on a school machine

nothing leaves

Why

  • Nothing leaves the school, which is the strongest POPIA position.
  • No cloud bill.
  • Already built: it is today's offline fallback.
  • Fits schools with poor connectivity, a real pitch point.

Watch

  • The demo laptop has no GPU (22 GB RAM, CPU only), so a 32-script set will be slow (unmeasured).
  • No live URL for the judges.
  • One machine is a single point of failure.

Option D · Claude on Bedrock in the EU

data crosses

Why

  • Likely the strongest reading of maths working and marking against a memo (to be measured).
  • No GPU for us to run.
  • The least new code: the Anthropic SDK has a Bedrock client.

Watch

  • Answer crops and pseudonymised text leave South Africa: s72(1)(a).
  • Per-token cost against the architecture plan's R40 per set.
  • Must use the EU profile from eu-central-1. Global inference would route prompts worldwide.

Two other ways to reach Claude, both weaker on the law. Bedrock global inference, the only Claude option offered from Cape Town itself, routes a prompt to "any supported AWS commercial Region worldwide", which raises s57(1)(d) for children's data. Anthropic's own API uses the same anthropic_provider.py already in the repo, but brings a second vendor contract and a bill outside AWS.

Option E · Hybrid: pages read in Cape Town, Claude marks the text

text crosses

Why

  • Claude's marking, while no handwriting or page image leaves South Africa.
  • Only pseudonymised text crosses, which is what the original plan assumed.
  • Its reader is option A's, so building A's reader first serves both.

Watch

  • Two quotas to secure (G4dn and Bedrock) and two bills.
  • The reader's accuracy on maths handwriting caps everything after it; the eval measures it.
  • Text still crosses, so s72(1)(a) applies.

08 · Regulation

Staying within the law

Learners are minors, so their records carry POPIA's strictest rules. Options A and C make no transfer of learner data. B, D and E rely on s72(1)(a), and E sends the least: text, never pages. The rest of POPIA applies wherever the servers are.

Children's records · s34, s35

Processing a child's personal information (anyone under 18) is prohibited unless an exception applies. The ones that fit a school are prior consent of a competent person (a parent, s35(1)(a)) or processing needed for an obligation in law (s35(1)(b)). Our reading: marking is a school's assessment duty, but this needs a legal check before Mothusi touches a real class. The hackathon uses synthetic scripts only (PROJECT-ARSENAL §7).

Sending data abroad · s72, s57

A transfer is allowed if the recipient is bound by law, rules or an agreement giving adequate protection (s72(1)(a)), or the person consents (s72(1)(b)). Sending a child's information to a country without adequate protection needs the Regulator's prior authorisation (s57(1)(d)). Option A makes no transfer of learner data. Option B would rely on s72(1)(a): AWS's data processing terms and EU regions, which are covered by GDPR. Option C keeps everything in the school.

Pseudonyms are still personal data · s1, s6

The Act stops applying only to information "de-identified to the extent that it cannot be re-identified again" (s6(1)(b)). Mothusi keeps the pseudonym map so it can return notes to the right learner, so the text the models read stays under POPIA wherever they run. Pseudonymising reduces the risk but does not take the data out of the Act.

Operators and breaches · s19–s22

The school is the responsible party; AWS and ElevenLabs act as operators. Under option C the school runs everything itself. Each needs a written contract requiring security measures and immediate notice of a breach (s21). Reasonable technical measures (s19) here mean KMS encryption, private subnets, Cognito sign-in and CloudTrail. A breach is reported to the Regulator and the people affected (s22).

Where data must be hosted

The National Data and Cloud Policy (2024) requires in-country storage only for government data on national security and sovereignty (15.4.2). We found no DBE or provincial rule on where learner data must be hosted. Option A keeps all learner data in Cape Town, at rest and while it is processed. That goes beyond what is required.

The voice · ElevenLabs

ElevenLabs stores data in the US by default. Its EU, India and Singapore residency still allows processing elsewhere, and its zero-retention mode is Enterprise-only (HIPAA/BAA). It has no Africa option. The voice carries the teacher's own speech (consent under s72(1)(b)) and sentences built by Mothusi's code from pseudonyms and counts, never a learner's name. Amazon Transcribe and Polly both run in Cape Town if that ever has to change.

09 · Decisions

What was decided, and what is still open

Each decision becomes an architecture-plan change by PR. A decision only counts once the architecture plan or the agreed scope on main says it. By 12 Nov ADRs 0001–0004 had settled most of them; the vLLM question is open again because of what the eval measured.

GPU capacity during the event

Research for the project researcher to decide on the day (deployment-aws.md §10). The window is Fri 13 Nov 07:00 to Sat 14 Nov 13:00 SAST, 30 hours, at g4dn.xlarge $0.698/h, the rest of the stack $0.289/h running and about $0.05/h stopped.

OptionWhat runsCost for the 30 hStart can fail on capacity?
1. Always onEverything, the whole window~$29.60The Friday start only
1b. Stop overnight (Fri 19:00 → Sat 06:00)19 h running, 11 h stopped~$19.30The Friday start and the Saturday 06:00 restart
2. Capacity Reservation, always onAs 1; the reservation covers the running g4dn (billed once)~$29.60The Friday start only
2b. Capacity Reservation, stop overnightReservation held 30 h; RDS and Fargate stopped overnight~$27.00The Friday start only; the Saturday restart is guaranteed
4. Second zone (af-south-1c), stop overnightAs 1b, plus a second host's 100 GB disk in 1c~$20, ~$0.20 to set up, then $10.47/month for the disk until deletedOnly if both zones are short at once

A Capacity Reservation is created or refused at once, and only while capacity exists, so it is made right after the g4dn starts. It is billed at the on-demand rate whether or not an instance runs in it. Options 1 and 2 cost the same; the reservation pays only if the host must be stopped or restarted mid-event. 2b over 1b is about $7.70 for a guaranteed Saturday restart. Option 4 costs about half a day of work and a VPC change the day before the event, and lowers the risk rather than removing it.
